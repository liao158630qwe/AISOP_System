# 服务器部署审查（2026-11-08）

当前工程已具备 PostgreSQL、HTTPS、持久数据卷、任务租约、最新帧有界调度、模型池、资源回收及告警归档等基础。服务器化应优先补齐阻塞隔离、容器更新恢复、退出协议和推理就绪检查，再按实际六工位模型调整容量。

审查依据是当前工作区，而非 Git 已提交版本。按仓库已有 Linux + Docker Compose + NVIDIA GPU 部署方案审查；历史配置指向双路至强 + RTX4090、六台工位机采集。此次未连接目标服务器，没有取得目标硬件的实测吞吐。本轮仅新增此报告、隔离故障探针和验证产物。

**优先处理的项目**

| 优先级 | 项目 | 当前证据与影响 | 建议 |
| --- | --- | --- | --- |
| P1 | 异步请求中同步访问数据库 | 登录及普通视频上传完成后的事务直接运行在事件循环；慢数据库会阻塞同进程其他请求 | 把完整事务移到线程池，或采用异步数据库驱动；补慢数据库与并发实时帧回归 |
| P1 | API 更新后的代理地址恢复 | Nginx 上游使用固定启动解析，缺少动态 DNS；API 容器换 IP 后存在持续 502 风险 | 使用 Docker DNS 动态解析，验证仅重建 API 后能自动恢复 |
| P1 | 容器退出和内部收尾不一致 | API 未设置停止宽限期；内部取证线程可等待 60 秒；Worker 没有 SIGTERM 停止入口 | 统一停止接单、排空、持久化、释放资源和容器超时；实际测试带任务停止 |
| P1 | 生产 GPU 工作模式不明确 | 默认实时、离线、训练共用 GPU，且全局实时并发默认只有 1 | 提供明确的实时生产与训练维护配置；按实际模型和显存测量配置容量 |
| P2 | 就绪检查未覆盖推理能力 | `/ready` 只看数据库和 Worker 心跳，未看模型准备结果 | 增加按已启用工位计算的推理就绪状态；管理服务与推理能力分别报告 |
| P2 | 多场景模型缓存可能反复换入换出 | `SCENE_MODEL_CACHE_SIZE=1`，不同模型交替请求会驱逐空闲模型 | 在显存允许范围内覆盖实际活跃模型，跟踪加载次数、驱逐率与冷启动时延 |
| P2 | 告警落盘占用实时请求容量 | 每个告警逐张 JPEG `fsync`，完成存储前仍占用推理准入名额 | 先量化告警时磁盘延迟，使用本地 SSD；再考虑保持耐久性语义的有界存储流水线 |
| P2 | 代理后的登录限流归属不准确 | Nginx 未传客户端地址，后端按 `request.client.host` 累计失败 | 明确转发头与可信代理范围，避免多个工位共用后端失败计数 |
| P2 | 长期运行交付不完整 | 有备份和采集器说明，但缺少可直接部署的备份、恢复演练和采集进程托管模板 | 补齐服务器运维包、容量告警及恢复验收；保持现有单 API 实例约束 |

P1 表示建议在生产验收前完成，P2 表示应纳入持续运行和容量验收。配置风险与本地故障复现分开说明，不把静态检查当作目标服务器故障实测。

**1. 数据库慢请求会拖住整个 API 事件循环**

位置：[backend/app.py](../../backend/app.py)，登录事务在 322–324 行，视频上传后的事务在 377–390 行。密码计算及视频探测已经转入线程池，但这两处数据库操作仍直接放在 `async def` 路由中。

隔离 ASGI 探针对登录 `INSERT INTO sessions` 注入 250 ms 延迟，确认 SQL 在事件循环线程执行，5 ms 心跳出现 **262.767 ms** 最大间隔。这是故障注入结果，不是正常登录时延，也不是目标 PostgreSQL 的性能测量。

推荐把整个事务封装为同步函数后用 `run_in_threadpool` 调用，连接的获取、使用和关闭应在同一个工作函数内完成。`backend/db.py:274–279` 已有连接池等待和建立连接超时，但没有应用显式设置的 PostgreSQL 语句/锁等待预算；后续按读写类型配置，避免慢 SQL 长期占用线程和连接。不要把池大小无限调高来掩盖阻塞。

验收：同时提交实时帧及登录/上传，在注入 SQL 延迟、连接池耗尽时，实时调度、取消和健康探针仍能及时运行。

**2. API 容器重建后，Nginx 需要重新解析上游地址**

位置：[deploy/nginx.conf](../../deploy/nginx.conf) 第 4–6 行、[compose.yaml](../../compose.yaml) 第 108–117 行。上游是 `server api:8000;`，没有 `resolver`、共享上游 `zone` 或 `resolve`；Web 对 API 的依赖只声明启动健康条件。

Docker Compose 服务重建时可能获得新 IP。当前写法没有配置随 DNS 变化更新上游，因此仅更新 API、保留原 Web 容器时存在继续请求旧地址的风险。本机没有 Docker 命令，此项未通过真实容器重建复现。

建议在当前 Nginx 1.28 配置上使用 Docker 内置 DNS `127.0.0.11`，配置共享上游区域和 `server api:8000 resolve;`，设置有界 DNS 缓存时间。Nginx 官方文档确认 `resolve` 从 1.27.3 起不再限于商业版。临时流程也可在 API 更新后显式重新加载 Web，但动态解析更适合日常运维。

验收：使 API 容器更换 IP，Web 不重建，确认 DNS 缓存期限后 HTTPS 请求恢复；同时验证视频上传、采样、Range 下载和内置鉴权仍然有效。

**3. 优雅关闭需要覆盖 Docker 和子进程**

位置：[compose.yaml](../../compose.yaml) 第 70–107 行、[backend/app.py](../../backend/app.py) 第 119–131 行、[backend/evidence.py](../../backend/evidence.py) 第 148–152 行、[backend/worker.py](../../backend/worker.py) 第 206–253 行。

API 已有顺序排空逻辑，但 Compose 只有 Worker 设置了 `stop_grace_period: 70s`，API 没有设置。Docker Compose 默认给容器 10 秒退出时间，之后发送 SIGKILL；取证收尾单项就可能等待 60 秒，模型准备线程的 `join` 也没有时间上限。因此 Python 内部关闭测试通过，不能说明实际容器停止时能完成收尾。

Worker 的主循环没有注册 SIGTERM/SIGINT，也没有主线程停止事件。仅有 `finally` 和 70 秒容器宽限期不足以构成完整停止协议；具体终止行为还取决于镜像入口和 PID 1 信号转发。训练 supervisor 在执行作业期间也没有持续检查外部 `stop`，需与子进程终止策略一起处理。

建议先定义可中断任务、可重试任务和必须持久保存的结果，再加入信号处理、停止领取、租约处理与子进程收尾；API 容器宽限期要覆盖实测排空预算，并为异常卡死提供上限。单纯增加超时不能解决所有关闭问题。

验收：模型预热中、六路推理中、告警编码中、训练中分别停止容器；重启后不出现重复归档、遗留计算进程或错误 PASS，任务按既定租约和中断规则恢复。

**4. 将实时生产和训练维护配置明确分开**

位置：[compose.yaml](../../compose.yaml) 第 12–24 行、[deploy/rtx4090-six-stations.env.example](../../deploy/rtx4090-six-stations.env.example)、[backend/app.py](../../backend/app.py) 第 150–157 行。

默认 `WORKER_ANALYSIS_ENABLED=true`、`WORKER_TRAINING_ENABLED=true`，推理和训练都指向 `cuda:0`。训练的 25% 限制来自 PyTorch 显存分配器设置，不能提供 GPU 算力或响应时延隔离。Worker 可以在实时检测期间同时分析离线视频和训练。

默认 `STATION_INFERENCE_CONCURRENCY=1`、`REALTIME_POOL_SIZE=1`；有效总容量取两者较小值。六路请求有排队和最新帧替换保护，但默认配置不是六路性能配置。

仓库已提供 4090 候选文件，其中关闭离线/训练、设置并发和人体池为 3；它不会自动生效。推荐将其转成可明确选择、可验证的部署配置。确需并行训练时，优先分离 GPU/机器或设置维护窗口；具体 GPU 可见设备及物理卡绑定应显式配置。

现场六种模型尚未确定，不能把并发 3、专项池 3 或任何单卡容量作为已验收参数。CPU 线程预算先沿用已有 4/4，再依据目标双路服务器 CPU、GPU、网卡拓扑测量；没有依据时不把线程数扩到所有 CPU 核心。

**5. 就绪状态应反映实际启用的模型**

位置：[backend/app.py](../../backend/app.py) 第 103–115 行和第 275–287 行。模型预热失败只记录日志，而 `/ready` 仅检查数据库和 Worker 心跳。

隔离探针中，配置的模型文件不存在，但有效 Worker 心跳使 `/ready` 返回 200、`status=ready`。探针没有启动应用 lifespan 或执行真实模型加载，仅验证该接口的判断条件；源代码另显示生产预热异常不会转为该接口的失败状态。

建议维护已启用工位所需模型的准备中、就绪、失败及最近错误状态，提供独立推理就绪检查或能力字段。不要要求所有可选模型都加载后才开放管理页面，也不要在每次健康检查中重新加载模型。Worker 退出和实时推理失败应能分别诊断。

**6. 多模型部署需要同时考虑驻留量和执行量**

位置：[backend/scene_realtime.py](../../backend/scene_realtime.py) 第 80–104 行、[backend/app.py](../../backend/app.py) 第 150–153 行。场景执行容量还受到 `SCENE_MODEL_CACHE_SIZE` 限制；当前默认和 4090 候选模板均为 1。

多个不同模型交替进入时，满缓存会驱逐空闲条目；它有内存上限保护，但可能反复冷加载。建议先测每个实际模型及组合显存，再设置驻留容量，预热实际需要的模型。即使驻留 6 个模型，也可以把并发执行限制在 2 或 3；两项参数不必相同。同一模型实例继续保持独占，不能通过取消锁来增加并发。

验收重点是 `modelLoads`、`evictions`、`busyRejections`、逐路有效 FPS 和 P95/P99；不能只看整卡 GPU 利用率。

**7. 告警保存会影响实时响应的尾部延迟**

位置：[backend/terminals.py](../../backend/terminals.py) 第 444–468 行、[backend/evidence.py](../../backend/evidence.py) 第 67–78 行和第 247–266 行。告警生成时，会逐张写 JPEG、刷新到磁盘并保存清单；全部完成后才归还准入名额。

这保留了可靠落盘语义，但磁盘忙、多个工位同时告警时，会占用实时容量。普通无告警压测不能覆盖该路径。

先用已有 `serviceTimingsMs.evidenceMs` 测量告警期间的 P95/P99，并将暂存放在可靠的本地 SSD。若确认为瓶颈，再设计有界写入队列、明确的 pending/durable/failed 状态及故障恢复；不能简单改成无界后台任务，也不能提前宣称证据已保存。归档和备份对推理盘的竞争应纳入满负荷测试。

**8. 修正代理地址和登录失败计数的关系**

位置：[deploy/nginx.conf](../../deploy/nginx.conf) 第 18–22 行、[backend/app.py](../../backend/app.py) 第 205–215 行和第 310–320 行、[deploy/Dockerfile.api](../../deploy/Dockerfile.api)。

Nginx 登录路由没有设置 `X-Forwarded-For`，后端按 `request.client.host` 统计失败；在此 Compose 链路下，多个客户端可能被归到同一代理地址，导致相互影响。Nginx 自身按来源地址的限流仍存在，不能据此认为后端的计数已正确区分终端。

建议由 Nginx 明确写入客户端地址，Uvicorn 只信任实际代理网络/地址；不要无条件接受外部伪造转发头。验证两个客户端中一方输错密码，不会封锁另一方。失败计数字典还应清理长期不活跃的来源项。

**9. 补齐可交付的服务器运维流程**

- 数据：目前有 PostgreSQL 和 `/data` 持久卷；[部署指南](../guides/server-quickstart.md) 只给出一致备份原则。需要具体备份命令、保存位置、恢复步骤和演练结果；数据库、业务媒体、模型版本及配置必须能对应恢复。
- 采集：已有常驻采集器及故障退出码，但 `deploy/` 没有相应 systemd/容器托管模板。若使用服务器直连 RTSP，补六路服务定义；若 USB 接工位机，采集进程仍需在相机所在机器运行。自动重启必须区分临时网络故障和需要人工复核的轮次终止，不能无条件重开流绕过检测时限。
- 容量：数据集上传有剩余空间检查；普通视频和模型上传没有同等的剩余空间/并发额度控制。补统一上传预算、低空间拒绝和告警，并覆盖模型、训练产物与训练日志的保留策略。Docker 日志轮转不覆盖 `DATA_DIR/training-logs/*.log`。
- 监控：已有指标接口，可接入外部采集与告警，覆盖逐路 FPS、结果年龄、最长无结果间隔、队列拒绝、模型重载、数据库时延、磁盘空间、告警归档失败和 Worker 心跳。不能把容器存活当作业务正常。
- 镜像：API 与 Worker Dockerfile 大部分重复且均装全量依赖，可抽取共同运行基础；进一步审查非 root 运行、可写目录权限和可复现依赖。先保持功能完整，不因缩镜像漏掉实际模型依赖。
- 扩容：工位时序和部分模型状态仍在 API 进程内。当前必须维持一个 API 实例、一个 Uvicorn worker。后续需独立推理服务和明确的流归属/状态协议，才适合横向扩容。

**现有性能证据及本次验证**

不应继续引用早期“六路每路 4 FPS”的结果作为当前唯一基线。较后续的[系统吞吐记录](system-throughput-2026-11-07.md)包含本机 RTX5070 Ti、每路目标 10 FPS、六路混合任务的六轮 30 秒实验：总有效吞吐约 25.834–35.700 FPS，最慢一路约 3.233–3.667 FPS；各轮均未达到六路分别 10 FPS。这些是历史测试，不是本次新测，也不等于目标 RTX4090 容量。

本次验证如下，原始产物位于 `test-results/server-audit-20261108/`：

| 验证 | 结果 | 范围 |
| --- | --- | --- |
| 服务器、稳定性、关闭、工位、取消、运行时、静态资源回归 | 113 passed，34.76 秒 | 当前本机；多数接口使用临时 SQLite 和模型替身 |
| PostgreSQL 并发、租约、管理及检测历史集成 | 7 passed，6.26 秒 | 独立 PostgreSQL 16.6、本地随机端口、临时 schema；零遗留测试 schema，测试数据库进程已停止 |
| 异步登录故障注入 | 复现事件循环阻塞 | 注入 250 ms SQL 等待，最大心跳间隔 262.767 ms |
| 就绪条件探针 | 模型缺失时仍返回 200 | 仅验证 ready 逻辑，没有应用 lifespan 或实际推理 |
| Linux Compose 构建、容器换 IP、容器停止 | 未执行 | 当前环境没有 Docker 命令 |
| RTX4090 六路真实采集、8/72 小时稳定性 | 未执行 | 未连接目标服务器，没有实际六模型和六相机输入 |

首次尝试仓库默认 PostgreSQL 测试端口时发现 15432 被占用，未接管或停止该进程；最终改用独立目录和随机端口完成测试。

实施次序建议：先修复 P1 与推理就绪状态，再发布明确的生产配置和运维包；随后以实际六模型完成单路、混合负载、告警密集、重连及长时间测试。逐路 10 FPS、响应时延和无结果间隔分别验收，不用总吞吐替代最慢工位指标。

**核对的官方资料**

- Docker Compose Networking：服务重建后的地址变化与重新解析责任。
- Docker Compose Services：`stop_grace_period` 默认 10 秒，以及 SIGTERM/SIGKILL 行为。
- Nginx HTTP Upstream：`resolve`、`resolver`、共享内存区域及版本要求。
- FastAPI 官方仓库 `docs/en/docs/async.md`：异步路由直接调用同步函数不会自动移到线程池。
