## 结果使用边界

- 正式目标为每路有效 10 fps，不能用总吞吐或平均帧率抵消慢工位。脚本中 95% 容差及默认 500 ms 门限仅为既有压测判据，不等于新增的现场协议。
- 六个浏览器的解码、编码和服务器模型共用本机资源；实际六台工控机分担这些工作，需在现场重新测量。
- 测试窗口为 30/60 秒级，不能据此宣称整班或 24 小时运行稳定，也没有评估现场漏检率。
- 各阶段 P95 是不同样本分布的分位数，不能相加还原端到端 P95。
- 数据库、模型配置及正式工位绑定未用于测试写入；测试脚本与原始数据保存在 test-results/terminal-performance-20261108 和各隔离运行目录。

## 本轮结论

六路螺丝页面可以同时运行、显示结果并归档，但当前实测没有达到六路各 10 fps。六路推理上限下，页面公共窗口每路约 2.98–3.57 fps，总计 20.28 fps；采样至结果 P95 为 420.6–482.9 ms。没有帧请求错误、结果身份错配或归档失败。这里的成功仅指本次短时功能链路，不代表长稳或准确率验收。

三路推理上限仍同时服务六个页面，其公共窗口每路约 3.59–3.69 fps，总计 21.73 fps，P95 为 396.7–409.6 ms。三个工位的首帧收到 HTTP 429，随后客户端恢复，六路最终均归档；这些拒绝已经影响窗口内有效 FPS，没有从统计中删除。

API 测试中，上限从 3 提高到 6 后，排队 P95 从约 172 ms 降为 0，但模型服务 P95 从约 165–174 ms 增至约 316–330 ms，总吞吐基本不变；整卡采样显存峰值从 7835 MiB 增至 11429 MiB。说明当前不能靠增加副本/并发解决容量问题，应继续对螺丝模型服务内部做性能剖析，区分 GPU 执行、同步等待和 CPU 调度。整卡 GPU 利用率不足 100% 不等于剩余算力可以直接兑现。

建议保留原三路推理配置，下一步针对真实螺丝输入做同模型合批/执行链路优化前的 profiler 定位，且保持定位、检测阈值与判定语义一致。3/6 两档各测一次，不能据此宣称已经找到最佳并发值。真实六台工控机应再测有线网络、摄像头、编码、显示及全班运行。

兼容性问题：原始 HEVC 样片在该浏览器环境未解码出画面，页面却继续尝试采样并报 OffscreenCanvas 尺寸异常。此次保留原始失败证据，并用带完整来源记录的 H.264 副本完成性能测试；产品的无有效画面提示/阻止启动仍需另行修复。
