# 服务器性能与实时判定整体审查（2026-11-07）

本次已修复过期采样进入推理、旧结果被错误刷新为实时、采样中断后最终结果未受保护、分类模型忽略非首位禁用类别、竖屏输入不必要缩小，以及准确率评测遗漏缺失帧等问题。增加了多核 CPU 线程预算和生产采样期间的 Worker 工作开关，并提供 RTX4090 六路部署候选配置。

**当前尚不能认定六路现场验收通过。** 本机混合六路测试仍未全部达到每路 4fps；已有贴条开发视频在完整 4fps、10fps 采样下均漏确认 R05。代码回归通过与现场模型准确率达标是两项独立结论。

- 本次实测机器：Windows、RTX5070 Ti（工具报告显存总量 16303 MiB）、Python 可见 16 个逻辑 CPU；不能把其结果直接换算为目标服务器容量。
- 审查覆盖部署配置、API、数据库与任务领取、采样上传与调度、流状态、时序判定、证据存储、模型运行、Worker、浏览器终端、常驻采集器与评测工具。重点修改有复现证据的性能和判定问题。
- 工作区原有大量未提交修改；本次以执行前的文件快照核对修改，保留原有工作。测试使用独立数据库、端口和数据目录，没有部署服务器或重启业务服务，也没有替换模型或降低判定阈值。

## 已修复问题

| 优先级 | 原问题与影响 | 本次修改与验证 |
| --- | --- | --- |
| 高 | 工位采样只计算队列时间，上传、鉴权与线程池等待可能使旧帧继续进入昂贵推理 | `station_scheduler.py` 从请求到达起计算期限；`terminals.py` 在模型执行前再次检查。过期返回 429，测试覆盖入队前过期与调度等待 |
| 高 | 客户端时钟暂停时，实际采样中断可能不被记录；工位归档未应用底层流的最终缺口保护 | `streams.py` 同时检查服务端单调时间；归档调用 `protect_result(..., final=True)`。缺口不能沿用此前的 PASS |
| 高 | 新结果仍在保存证据时就刷新时间戳，状态查询可能把上一帧过期结果显示为 LIVE | 证据处理完成后，在事件循环内一起发布结果、预览和时间戳；阻塞证据写入的回归测试确认旧结果保持 STALE |
| 高 | 场景分类只检查 top1，正常类别 0.55、禁用类别 0.45 时，禁用阈值即使为 0.30 也会漏判 | 校验完整概率向量，检查所有已配置规则对应类别，再按各自阈值判定；非法概率失败。未改变已有阈值，可能使原来漏判的禁用类别正确触发 FAIL |
| 高 | 准确率脚本把 set 转为 int 导致运行失败；缺失预测帧被跳过会掩盖漏检 | 修正布尔计数，缺失帧按空预测计入漏检，输出覆盖率；全部缺失也生成报告。显式校验 split、跨 split 复用、时间与帧率，二分查找匹配帧 |
| 中 | 双路多核机器的 PyTorch/BLAS 默认线程数可能过多，多个推理组争抢 CPU | 增加 `TORCH_THREADS`，默认 4，合法范围 1–16，inter-op 固定 1；API/Worker 在 GPU 初始化前应用，指标返回实际线程数。Compose 同步设置 BLAS 环境预算 |
| 中 | Worker 的离线分析和训练可与实时采样争抢同一 GPU | 增加独立分析、训练开关，默认保留旧行为；RTX4090 候选配置关闭两者。验证关闭分析后仍执行心跳、清理与证据维护 |
| 中 | 1080×1920 贴条竖屏被宽高上限压缩为约 607×1080，损失小目标细节 | 浏览器、采集器与压测器对贴条/场景采用长边 1920、总像素 1920×1080 的边界；保持宽高比、不放大。姿态与螺丝保持原尺寸边界，JPEG 仍限 1MiB |
| 中 | 工位帧上传没有匹配 Nginx 的实时采样专用 location | 同时覆盖通用和工位帧路由，关闭代理缓冲、限制 1MiB 与 5 秒请求体间隔；API 在扩展缓冲前检查大小，提前拒绝超长 Content-Length |
| 低 | 已使用 CUDA 的 Ultralytics 预测器可能仍被状态页报告为 CPU | 状态优先读取已初始化预测器的执行设备；单元测试覆盖包装模型为 CPU、预测器为 CUDA 的情况 |

`STATION_QUEUE_WAIT_MS=500` 是开始模型执行前的采样年龄预算。推理开始后不会被强制打断，因此不保证整个响应在 500ms 内完成。`queueWaitMs` 仅含调度等待，`serverProcessingMs` 现在包含证据保存。

全部报告的 `allTargetsMet=false`，压测工具退出码 1 表示容量目标未满足。基线总吞吐约 8.53fps，混合并发约 17.6fps；主要来自启用项目已有的不同算法组并发参数，不能把这项增幅归因于本次代码修复。修复后串行约 8.2fps，严格拒绝旧帧本身并不提升 FPS。

以上是短时探索，未进行多轮随机顺序对照；首轮基线还与少量测试有短暂重叠。Torch 2 与 4 的数据不足以证明哪一个稳定更优，候选配置保留 4。最后一轮才使用保留竖屏细节的新采样尺寸，不能把所有轮次当作严格同条件比较。

原始数据位于 `test-results/station-gpu-benchmarks/` 上述各目录的 `report.json`、`settings.json`、`api.log` 与 `hardware.txt`。

## 录制视频的判定与瓶颈

执行 `tools/evaluate-realtime-fps.py --backend yolo --tasks sticker screw`。测试经隔离的进程内 API 执行真实模型，排除实体摄像头、网络、浏览器及预先完成的 JPEG 编码。完整模式处理指定采样率的每一帧，不能用其采样率标称值代表实时吞吐；节拍模式按真实时间到达并跳过处理不及的输入。

素材是已有的螺丝视频 `VID_20261017_103101.mp4`（0–52.5s）和贴条视频 `lv_0_20261017162449.mp4`（14–49.5s）。**两者属于开发/训练来源素材，标注也非独立测试集，因此下述结果不代表现场准确率。**

螺丝未完成品 FAIL、完成品 PASS、空白画面 REVIEW 的 4fps/10fps 对照均符合预期。贴条空白画面 REVIEW、只展示完成品 REVIEW、人工重排动作片段 FAIL 的对照也符合预期，但正确流程仍存在漏确认。

贴条 10fps 完整模式中，`inspection` 阶段中位数 **204.85ms**，人体检测 11.00ms、解码 5.42ms，说明主要时间在贴条专项检查。其内部含 CPU 图像配准等工作；此阶段总计时尚不能量化每个子函数的占比，也不能据此承诺更换 RTX4090 即可解决。

R05 的 10fps 检查区间内最高 contact 概率只有 0.3141；4fps 则有一帧达到 0.9433，但未形成连续动作证据。因此问题同时涉及分类稳定性和时间证据，单纯提高采样标称 FPS 或降低阈值不足以证明正确。当前没有调整模型、规则或阈值来让这一开发视频通过。

下一步应围绕 R05 采集独立人员、批次、光照、遮挡及相机偏移视频，复核位置配准与动作标注；按完整视频/工件划分训练、验证、测试。只在训练与验证集合改进模型，再用未参与调参的测试集报告各位置召回、缺件误放行、误报警和工件级结果。对性能，应先细分贴条检查中的配准、特征提取和分类耗时，再验证缓存或缩小计算区域是否保持几何可靠性；本轮没有引入未经验证的跨帧位置复用。

报告与逐帧证据：`test-results/server-review-2026-11-07/video-evaluation/`。模型与配置哈希检查 `unchangedAtEnd=true`；测试结束残留螺丝/贴条流均为 0。该次报告中的人体设备字段为旧诊断逻辑输出的 CPU；推理调用指定 CUDA，随后已修复诊断取值并增加回归测试，原始报告未篡改。

## RTX4090 六路候选配置及验收

把 [候选参数文件](../../deploy/rtx4090-six-stations.env.example) 的非敏感值合并到服务器 `.env`；该文件不是完整 `.env`，没有自动应用。配置以三种算法混合六路为参考：并发 3、人体池 3、OpenCV 4、Torch 4、场景缓存 1、数据库池 5+5。关闭 Worker 的离线分析与训练领取，避免与生产实时采样争用 GPU；排队任务保留等待，清理、心跳和 CPU 数据集抽帧继续工作。

这些开关在进程启动时生效，不抢占已运行任务，也不控制其他手工 GPU 作业。维护时恢复开关并重建 Worker；有在途任务时按已有维护流程处理。CPU 数据集抽帧仍有 CPU/磁盘开销，应在六路验收时一并考虑。

目标服务器先完成容器与 GPU 的启动检查：

```sh
docker compose config --quiet
docker compose up --build -d
docker compose exec web nginx -t
docker compose logs --tail=100 api worker
```

随后核对 `/api/v1/metrics` 返回的 GPU 与实际线程数，确认模型池容量及 Worker 模式，按六路真实任务类型和机位预热。使用独立测试配置复现本机混合负载：

```sh
python tools/benchmark-stations-local.py --profile mixed --fps 4 --duration 300 --concurrency 3 --pose-pool 3 --torch-threads 4
```

上述脚本自行创建隔离 API/SQLite 和测试身份；这只是模型/调度对照。目标部署的 PostgreSQL、HTTPS 与代理路径另用六个已登记测试工位的凭据验收。先在环境中配置 `AISOP_TERMINAL_KEY_1` 至 `AISOP_TERMINAL_KEY_6`，图像必须对应各工位任务；该命令会开启并关闭测试采集轮次，应使用验收工位与维护窗口：

```sh
python tools/benchmark-stations.py --server https://SERVER --fps 4 --duration 300 --deadline-ms 500 --report test-results/rtx4090-six-stations.json --images station1.jpg station2.jpg station3.jpg station4.jpg station5.jpg station6.jpg
```

工具当前通过标准为每路有效 FPS 至少达到目标的 95%，且 P95 不超过指定期限。正式现场还需使用六台真实摄像头持续覆盖完整生产轮次，检查长时间无结果、丢帧、断流、重连、归档、模型变更、CPU/显存/磁盘增长与各工位判定；重复图压测不能替代这些检查。采样目标还应以动作持续时间及独立视频结果确定，不能为了满足吞吐而任意降低动作检测 FPS。
