# 8000 主服务与实时交互优化验收

依据《灯具装配行为分析与工序时序合规系统优化方案》落实当前代码可实现的服务入口、实时交互、证据有效性和恢复保障。保留既有螺丝、贴条、人体、发布场景及工位1人工流程，不改变训练权重或现场工艺阈值。

## 本次实现

- 本机 `npm start`、`npm run dev:local`、`npm run preview` 统一启动 `127.0.0.1:8000` 的 API 和 Worker。启动器核对进程归属、端口、健康及登录配置，补启缺失服务，防止重复启动。`npm run status:local` 可检查状态，`npm run restart:local` 重启本项目服务。
- 页面、API、视频产物与管理页面使用同一来源。静态资源按内容版本更新；文本响应使用轻量压缩；Nginx 配置连接复用及实时请求禁缓冲。
- 实时请求在通用线程池之前执行有界准入。同流同时只处理一帧，忙时返回 `429` 和 `Retry-After`；重复、倒序帧被拒绝。实时接口不排队积压旧帧。
- 前端只保持一个在途采样，超时可取消，繁忙时按服务端提示退避。页面隐藏及摄像头中断停止提交旧画面；切换任务后迟到响应不能污染新任务。
- 开始实时检测时先显示“模型准备中”，使用独立临时流完成首次模型加载，再释放临时流并创建正式检测轮次。准备期间保持视频预览；准备帧不计入工序证据、采样缺口或正式延迟统计。取消准备不会生成工序判定，准备请求最长等待60秒。
- 画面新鲜度从采集时刻计算，超过750ms撤销当前标注及当前通过提示。本轮确认历史保留，显示为历史证据。
- 客户端和服务端记录超过3秒的采样间断，结束时有缺口的原始PASS转为REVIEW，并保留原始结论与缺口来源；已有FAIL不被覆盖。最后一帧仍在服务端执行时不提前结束判定。
- 页面显示浏览器采集至结果更新时延，并在运行详情中提供P95、P99及最大值。`/api/v1/metrics` 增加各类实时服务的并发、拒绝数和服务端时延。
- 离线任务长轮询支持最多5次有限重连，沿用任务编号和游标；不自动重新上传或重复创建任务。
- 工位1每5秒同步服务端状态，周期未变化时保留人工勾选。断线显示上次记录并禁用提交，恢复后重新核对工件。摄像头在确认弹窗期间断开时，使未发送的确认失效。
- 工位1阶段截图携带取证时间；未提交旧截图超过2分钟时拒绝重试，已提交请求可继续幂等取回。结束时按实际取证时间检查螺丝证据有效期。兼容旧客户端未携带取证时间的请求，旧接口仍按原接收时间口径记录。

实时流的缺口和最终响应目前保存在当前流内存状态中，释放或重启后不会形成永久生产履历。工位1人工周期、证据和审计事件使用数据库及文件持久化。不能把两者混为已交付的全线追溯系统。

## 验证结果

后端回归：252通过、1跳过；跳过项需要独立PostgreSQL测试服务。本机使用SQLite，PostgreSQL及Docker/Nginx部署未在本环境实际启动验证。

浏览器回归覆盖：完整工位1流程、丢失响应幂等重试、刷新恢复、复核返工、后台同步保留勾选、离线标记、相机断开撤销未提交确认、移动端。实时传输15项检查通过、页面异常为0，覆盖独立模型准备、准备期间取消及任务切换、超时、迟到响应、背压、隐藏恢复、缺口上报及离线任务同编号重连；模拟准备耗时超过3秒也不会误报生产采样缺口。管理目录的9项Node测试通过。

真实模型通过8000入口验证人体、螺丝、贴条三类摄像头路径，输入为录制视频驱动的浏览器摄像头，页面异常为0。人体另验证真实视频上传、独立Worker、回放、骨骼绘制及任务切换。

续验再次通过后端252项、管理目录9项、实时传输15项、工位1流程和人体上传回放。螺丝上传脚本原先依赖已缺失的历史截图与任务记录，已改为自动生成参考图视频、建立隔离数据库及API/Worker；重新通过历史打开、连续两次上传、原生文件选择、真实模型分析与回放、清空或损坏的列表节点恢复、无效输入及忙时提示。该视频为重复参考图的合成测试素材，只验证链路，不作为识别精度样本。记录与截图位于 `test-results/screw-upload-tests/run-fydkq1b2/`。

场景管理真实端到端验证通过：模型导入与上传、ROI、草稿与发布、禁用与启用、首页入口、独立Worker分析、视频回放、历史版本冻结、报告、移动端、摄像头推理、过期结果清除及会话过期。该验证使用隔离数据库和临时场景。

### 浏览器实时链路实测

重启主服务后，在本机RTX 5070 Ti环境依次测量三种任务，每种正式采样12帧。浏览器用录制视频作为摄像头输入，计时范围是浏览器采样开始至结果更新到页面；不包含相机曝光、驱动缓存和显示器最终扫描。准备时间单列，稳定阶段统计其余11帧，因此本次小样本P95与最大值相同。

| 任务 | 模型准备ms | 正式首帧ms | 稳定阶段P95 / 最大ms | 实际采样fps |
| --- | ---: | ---: | ---: | ---: |
| 人体 | 2317.7 | 202.1 | 35.5 | 3.91 |
| 螺丝 | 2334.9 | 190.5 | 191.9 | 4.04 |
| 贴条 | 1106.8 | 314.1 | 366.0 | 2.93 |

本次36个正式样本均小于500ms，三种任务均无采样缺口，所有API请求使用8000同源入口，结束后释放摄像头与实时流。这是依次运行的短时验证，不能外推为15路并行或长期时延上限。服务端`realtimeTransport`统计包含准备请求，不能直接与此处剔除准备阶段的浏览器统计混用。

原始JSON与截图：`test-results/service-optimization-20261105/main-service/`。修复准备阶段前的记录保留于`main-service-before-preparation/`，便于核对首次模型加载导致请求超时和缺口的原问题。

### HTTP基准

`tools/benchmark-service.py` 使用15个HTTP客户端，并在推理测试中提交提供的静态图片。每类结果剔除首个预热请求后统计12个成功样本。

| 场景 | HTTP成功样本 | 平均耗时ms | P95 ms | 最大ms |
| --- | ---: | ---: | ---: | ---: |
| 健康接口15客户端 | 180 | 9.34 | 10.96 | 27.61 |
| 人体图像推理 | 12 | 18.16 | 33.87 | 33.87 |
| 螺丝参考图推理 | 12 | 154.45 | 176.75 | 176.75 |
| 贴条参考图推理 | 12 | 353.67 | 394.32 | 394.32 |

15个独立推理流的过载验证共195次请求：146次成功、49次按容量限制返回429；每个流均取得有效样本，健康接口180次成功。成功请求中剔除各流首次请求后，P95为28.18ms，最大54.77ms。该测试使用同一幅人体静态图，只证明本次负载下有界处理和可用性，不代表15路实际视频按现场冻结频率运行。

原始记录位于 `test-results/service-optimization-20261105/`。这些是短时样本，无法证明长时间时延上限。前后测的缓存及预热状态不完全相同，不据此宣称识别精度或整体吞吐提升百分比。

## 运行与复测

```powershell
npm start
npm run status:local
npm test
npm run test:pilot-ui
npm run test:realtime-ui
npm run test:person-ui
npm run test:upload
npm run test:management-ui
npm run benchmark:service -- --clients 15 --samples 12
npm run test:main-service
```

主服务实测需要 `.runtime/local-settings.json` 登录配置及 `.runtime/screw-live-camera.y4m` 录制样本。测试不会创建生产工位周期；独立工位、人体和场景测试使用隔离数据库。`status:local` 的Worker指标表示进程存活，不是业务进度心跳。

`test:upload` 使用隔离数据库、临时API/Worker及自动生成的参考图视频，需要本机真实模型与推理依赖。`test:main-service` 默认每类12帧，可在PowerShell中用 `$env:AISOP_TEST_SAMPLES='101'` 调整到每类101帧，并用 `$env:AISOP_TEST_OUTPUT='test-results/service-optimization-20261105/main-service-recheck'` 指定独立输出目录；JSON同时记录时间、采样数、P95、P99和最大值，保留功能检查与500ms测量结果各自的状态。
