# 六工位 Windows 触摸终端优化方案

日期：2026-11-08。范围：6 台 27 寸 Windows 工位终端，展示 SOP、AI 画面、OK/NG、告警，并执行人工 NG 确认。

本文依据当前工作区源码和既有测试记录提出实施方案。2026-11-08 按“暂不使用独立终端”的当前范围，先落实第 5 节的主界面采样、结果新鲜度和画面优化；常驻进程远程控制、SSE 和媒体网关仍为后续方案。未改动设备绑定、数据库或部署参数，未执行现场六机性能测试。历史测试结果注明原环境，不作为当前六机验收结果。

## 1. 建议实施顺序

先统一工位操作入口并补齐确认可靠性，再优化采样、显示和生产部署，最后按实际六路模型定位服务器瓶颈。沿用现有工位、检测轮次、流代次和设备权限，不必重建整套业务。

| 优先级 | 工作 | 完成后的行为 |
| --- | --- | --- |
| P0 | 统一工位客户端入口 | 操作员在同一页面查看 SOP、画面、判定、告警和人工确认；固定本机工位权限 |
| P0 | NG 确认持久保存与结果核对 | 请求超时显示待确认；重启后能够核对原请求；服务端已保存的确认不重复写入 |
| P0 | 正式采集与检测轮次控制 | 界面刷新不意外中止后台采集；每件的开始、结束、归档与异常中断有明确边界 |
| P1 | 采样、显示与状态更新优化 | 最新帧有界发送；收到结果及时显示；画面和检测结果身份一致 |
| P1 | 六工位生产部署和测量 | 有线连接，记录每路实际带宽、有效 FPS、延迟、采样缺口与资源占用 |
| P2 | 根据瓶颈优化模型服务 | 对实际模型分段剖析、评估合批或部署优化，并验证准确性和时序结果 |

## 2. 当前系统已经具备什么

| 能力 | 已核对的实现 | 对后续工作的影响 |
| --- | --- | --- |
| 工位与设备权限 | `backend/terminals.py` 的绑定、独立凭据、会话和流租约 | 复用现有身份，不靠 URL 参数确定操作权限 |
| 固定工位主界面 | `backend/app.py` 向已认证终端的首页注入固定绑定；`frontend/screw-dashboard.js` 限制工位选择 | 可将现有主界面整理为操作员入口，无需另建一套确认 API |
| 主界面采样流水线 | `frontend/station-detection.js`、`frontend/station-frame-worker.js` | 已可在等待响应时准备下一张图片；最多一个上传请求和一张最新待送帧 |
| 简版终端 | `frontend/terminal.js`、`frontend/terminal.html` | 仍逐帧完成编码和请求后再采下一帧；状态查询完成后等待 500 ms 再轮询；页面没有人工复核操作入口 |
| 人工复核 | `backend/terminals.py::review` 与 `frontend/station-detection.js::showManualReview` | 已保留算法原结果，并按相同请求编号、结论和原因实现重复提交去重；新方案应复用 |
| 结果失效保护 | `frontend/terminal.js::renderStatus` 与服务端状态接口 | 已校验工位、相机、流代次、帧号并隐藏过期结果；优化期间继续保留 |
| 常驻采集 | `tools/station-collector.py` | 已有独立采集进程、单张最新帧缓存和 HTTP 连接复用；还需产品化服务安装、状态管理及每轮开始/结束控制 |

独立 `/terminal` 和首页固定工位模式是不同实现，不能将一处已完成的优化视为另一处也已具备。当前人工复核界面中的请求编号保存在弹窗闭包中；没有在这条确认链路中发现跨页面重载的持久待发送记录。

## 3. 工位软件与 27 寸界面

推荐将已支持固定工位权限的主界面作为统一操作端，提取共用采样和复核模块。简版 `/terminal` 可承担设备登录和诊断入口，避免长期维护两套不同的检测行为。

建议的触摸布局：主区域显示画面，右侧显示当前 SOP 步骤和判定，下方固定开始、结束、NG 确认及告警操作。关键操作保持可见；采用大按钮、明确的文字状态和足够间距，在现场实际分辨率、Windows 缩放和戴手套条件下验证。27 寸本身不足以确定布局尺寸。

SOP 内容建议按工位和任务绑定版本，缓存最后一次有效发布的内容；离线时标明版本与同步状态。实时 AI 状态单独显示，不能因为仍能查看 SOP 就显示检测在线。

可复用网页界面形成 Windows 客户端，提供开机启动、固定工位、受控设置入口和版本更新。如果最终采用浏览器全屏运行，应在交付文档中明确形态；需要安装式 C/S 软件时，再增加本地宿主、服务安装和升级组件。

Microsoft Edge kiosk 支持指定网站全屏，但官方说明其运行于 InPrivate 会话。因此不能把设备长期身份、待提交业务记录仅寄托在该会话的浏览器存储中。应由本地持久服务保存，或选择经过验证的持久客户端配置。

## 4. NG 确认与断线恢复

沿用当前业务语义：对已经归档、算法为 FAIL/REVIEW 的轮次进行人工合规/不合规复核，原算法判定保留。告警“已读”与修改最终人工结论应是不同操作。现有接口拒绝对运行中、中断或纯姿态轮次直接执行此类复核。

推荐提交过程：

1. 操作员选择结论，客户端生成唯一请求编号，并先持久保存工位、检测轮次、结论、原因和确认人的已认证身份。
2. 提交原请求。界面显示提交中，服务器返回已保存结果后显示成功。
3. 超时或断网时，保留同一请求编号和内容，显示待核对；这时不能推断服务器未保存。
4. 网络恢复后查询该轮记录。如果服务端已保存相同确认，则标记完成；尚未保存且仍允许操作，再发送原请求。
5. 如果该轮已被他人确认、权限变化或内容冲突，则显示实际服务器结果并停止自动重试。

本地记录需要跨进程重启保留。安装式客户端可在本地服务中使用 SQLite 等持久存储；网页方案需验证持久存储生命周期。设备凭据代表工位设备，当前设备复核记录的 reviewer 可为工位编号；若要求追溯具体员工，需要增加经服务器认证的工号/登录会话，不能直接信任客户端自报姓名。

实时采样继续只发送最新帧，不能在断网后把旧帧当实时数据集中补传。业务确认可以可靠重试，证据文件可以另设有界上传队列，三者采用不同恢复规则。中央推理连接中断时显示无法检测；恢复后按现有租约和轮次规则重新核对状态，不能将断线前的 OK 延续为新轮结果。

## 5. 采集、画面与通信优化

### 5.1 先优化现有主界面的采样与结果显示

当前使用首页工位 1–6 检测入口，不启用独立 `/terminal` 作为本轮优化入口。主界面继续直接使用帧接口的检测结果，无需额外轮询才能更新判定；状态接口用于运行详情核对。帧响应同时核对工位、工位机、相机、绑定版本、流 ID、流代次、检测类型、场景、模型版本和帧号。

保留并验证现有“编码与上传重叠、一个在途请求、一张最新待送帧、过期丢弃”流水线：新采样替换待送旧帧，采图后超过 500 ms 的帧不再上传，收到忙碌响应遵守退避时间。运行详情新增本轮采图、提交、替换、过期、丢弃、请求失败和迟到结果计数，便于区分采图、编码及请求耗时。

即时结果的 1 秒有效期改为从浏览器采图时刻起算，不能从收到响应时重新计时。已经超时的响应不恢复当前判定、识别框，也不触发自动结束；已归档结论仍按历史记录展示。这个时间包含编码、待送、请求和服务器处理，不包括相机曝光和驱动缓存。

页面切后台、断网、视频暂停或相机静音时清空待送帧并使现有结果失效；恢复后只允许新采样刷新判定。停止或归档先禁止新采样并关闭编码，再等待正在编码和上传的任务收尾；收尾响应不能重新显示已停相机的画面或清除故障提示。归档响应必须确认身份、帧号范围以及 `final=true`、`archived=true`，之后才释放流；响应不完整时保留本轮供重试。

### 5.2 常驻采集需要完整的轮次控制

本轮保持主界面直接采集，暂不接入后台采集远程控制。以后需要关闭或刷新页面仍持续采集时，可复用 `tools/station-collector.py`，由 Windows 服务管理器负责启动、异常恢复与日志，主界面负责操作和显示。

当前常驻采集器不能直接视为完整的操作员客户端：文档已说明网络终端没有远程控制常驻进程的按钮。需要增加经过鉴权的开始、停止、结束并归档命令，确保只有对应工位的生产者执行；结束时停止新采样、排空在途请求、调用 finish 后释放流。相机和服务器重启继续将不能完整恢复的轮次记为中断。

### 5.3 按需采用事件推送与独立预览

对于后台采集和集中大屏，可增加按工位鉴权的 SSE 状态推送，携带工位、流代次、帧号和结果时间；心跳、重连及重新读取快照由应用实现。SSE 是服务器到客户端的单向通道，人工确认仍走现有 HTTP API。断线重连本身不保证业务事件不丢失，已归档记录和告警仍以数据库为准。六台机器的轮询量本身不能直接判定为瓶颈，是否迁移以实测刷新延迟和请求负载决定。

主界面的摄像头与视频来源现在可切换“检测采样与识别框”和“实时视频（无识别框）”：前者在对应采样快照上绘制识别框，后者播放本机视频并明确标明判定来自最近有效采样。图片联调继续显示对应采样，不显示视频预览帧率。

视频预览帧率取浏览器呈现的视频帧计数；有效检测帧率按最近 10 秒成功返回的检测帧计算，不足 10 秒按本轮实际运行时长计算，停止后冻结统计。两者在页脚和运行详情分别显示，不以预览流畅程度代替检测吞吐。浏览器不支持视频帧计数时显示“—”。

RTSP 当前无媒体网关时展示的是检测 JPEG 采样画面，不能承诺连续高帧率视频。若现场要求流畅视频，再增加同源鉴权的媒体网关并测量延迟。本轮未新增 SSE 或媒体网关。

本轮实现与验证结果见[首页采样与预览优化记录](../history/capture-preview-optimization-2026-11-08.md)：23 项浏览器流水线场景、六工位完成归档、人工复核回归及 17 项静态资源检查通过；模型响应为测试样例，不是现场性能验收。

## 6. 网络和服务器

建议六台终端采用有线千兆网络。交换机端口按终端、服务器、相机及上联分别统计，预留扩展。服务器链路容量按所有入口和出口的总负载决定。

本系统当前上传 JPEG 图片，不能直接套用 H.264/H.265 连续视频码率：

```text
图像负载 Mbps = 平均 JPEG 字节数 × 每路有效发送帧率 × 路数 × 8 / 1,000,000
示例：300,000 字节 × 10 fps × 6 路 × 8 / 1,000,000 = 144 Mbps
```

上述仅为假设示例，不是现场测量；还需计入预览下载、证据上传、其他业务及协议开销。先记录真实 JPEG 大小分布和每工位吞吐，再决定服务器上联是否需要更高带宽。不能仅为降低网络流量就缩小小零件图像，输入尺寸或压缩质量变化要验证识别效果。

保留当前单 API 实例、单 Uvicorn worker 的限制：时序状态和即时结果保存在进程内，不能直接通过增加 worker 数扩容。现有 `deploy/rtx4090-six-stations.env.example` 是候选配置，不等于正在运行的配置，也不构成达标保证。

生产期间可应用现有离线分析与训练禁领开关，避免与实时任务争用 GPU；在受控维护窗口应用。按六路实际模型测量驻留显存与预热耗时，再设置模型缓存和并发。相同模型合批只在输入和时序约束兼容、等待时间有界的条件下评估；不同权重不能作为同一推理批次。

2026-11-07 的系统吞吐记录中，本机 RTX 5070 Ti、姿态/螺丝/贴条各两路、重复 JPEG 的 30 秒测试，某组六并发配置总有效帧率为 35.700 fps，最慢一路为 3.233 fps；该轮队列 P95 已为 0。它提示应继续剖析模型服务内部耗时，但没有证明现场网络或目标服务器的瓶颈。该测试不含六台工控机、相机采集和页面显示，不代表六路各 10 fps 已验收。

## 7. 验收方法

先在隔离环境完成功能和故障注入，再在实际六机、相机和服务器上测试。建议覆盖至少一个完整生产班次，长稳测试时长作为新增验收项单独确定。

| 项目 | 检查内容 |
| --- | --- |
| 吞吐 | 项目文档目标为每路有效 10 fps、总计 60 fps；逐路报告，不以平均值替代慢工位 |
| 延迟 | 分开统计采图、编码、上传、排队、推理、取证、结果返回和显示的 P50/P95/P99；各工序延迟限额待现场定义 |
| 新鲜度 | 当前结果年龄指标从服务器收到 JPEG 起算，不覆盖曝光和相机缓存；端到端延迟需额外采集时间或外部测量 |
| NG 确认 | 模拟服务器保存成功但响应丢失、重复点击、刷新、客户端重启及多人冲突；原结论保留，同一确认只生效一次 |
| 断线 | 拔网线、相机重启、API 重启、服务崩溃；无旧 OK 残留、无错误跨轮续接，恢复后状态可核对 |
| 现场画面 | 实际 27 寸屏和 Windows 缩放下完成触摸操作；画面/结果对应正确，不因小目标缩图导致漏检 |
| 长稳 | 持续观察内存、显存、待发送记录、证据积压、磁盘增长和重连次数；不存在无界积压 |
| 识别效果 | 输入、并发或模型执行优化后，对独立现场样本检查漏检、误判和完整工序结果 |

第一批建议交付：固定工位操作入口、现有采样模块复用、人工复核入口、持久待确认记录和断线核对。SSE、媒体网关、模型合批按后续测量结果推进。
