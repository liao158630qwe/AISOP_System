# 后端稳定性与技术协议对应说明

2026年11月6日。本轮依据桌面《技术协议.docx》的第2.3、4.2、4.3、5、9节，优先修复现有后端的数据保留、故障恢复和并发状态问题。运行验证已经完成；协议全部功能与现场KPI仍需逐项验收。

## 已落地的运行保障

| 协议关注项 | 实现与作用 |
| --- | --- |
| 记录与证据可靠保留 | 清理保护运行中、取消中和排队任务的输出目录；仅处理超过保留期的终态记录。先提交元数据变更，再删除文件；事务回滚不会留下丢失文件的有效记录。 |
| 持续运行 | 清理以每类最多500条记录分批处理，文件IO在事务之外；单文件删除失败记录错误并在后续重试，清理异常不阻塞任务领取。避免将全部任务JSON载入清理内存。 |
| 异常后恢复 | Worker异常退出后按租约重新领取；旧token无法提交。数据库短暂中断保留任务供恢复，不误标为用户取消。缺少可选推理依赖会结束对应任务并记录错误。 |
| 多终端状态 | 每个检测服务保留最多32路状态，每个会话最多16路，闲置有效期300秒。满载拒绝新流并返回429，已有流不会被静默挤掉。此容量是状态数量，不是GPU并行推理槽位。 |
| 工序证据连续性 | 流的模型或画面配置变化返回409；过期流要求重开。状态重建且首帧时间超过3秒时标记证据缺口，原PASS降为REVIEW。重启不承诺恢复内存中的自动检测状态。 |
| 并发操作一致性 | 采样、结束与释放互斥；最后一帧在途时结束或释放返回429。重复结束保留已有结果。 |
| 数据库断线 | 返回503和Retry-After，不回传SQL/连接信息。写入结果不确定时保留上传文件；媒体和模型注册尝试查询已提交结果。带幂等键的操作使用原键重试。 |
| 设备/服务状态 | 新增Worker数据库心跳、存活和就绪接口；Compose和本机启动器依据就绪检查识别API在线但Worker失联的情况。 |

`RUN_RETENTION_SECONDS=2592000`保持分析记录默认30天；`UPLOAD_RETENTION_SECONDS=604800`仅清理不再被任何保留任务引用的旧上传。人工工位的证据和追加审计日志不由该清理器删除。实时帧当前没有自动录像，这些保留设置不能替代协议要求的30天告警录像。

清理路径限制在DATA_DIR的uploads和runs目录，拒绝越界路径、符号链接和目录跳转。`server:cleanup -- --dry-run`只预览；无参数执行会按配置移除过期分析记录。

## 运行与升级

在项目根目录执行：

```powershell
npm run restart:local
npm run status:local
```

启动器先初始化数据库，新增`worker_heartbeats`表，已有表和记录保持兼容；随后启动API和Worker并等待就绪。直接运行服务或更新容器时，应先执行`python -m backend.init_db`，再同时更新API和Worker。Compose的`init`服务会执行初始化。

初始化会为已有数据库补建媒体引用、终态清理和媒体创建时间索引，减少清理和引用检查对全表扫描的依赖。本轮应用到本机服务前已备份SQLite数据库到`.runtime/backups/`。

| 接口 | 用途 |
| --- | --- |
| GET /api/v1/live | 进程存活，不查询数据库；不可用于判断业务可用。 |
| GET /api/v1/health | 保留旧API健康契约，检查数据库与原能力字段。 |
| GET /api/v1/ready | 数据库可查询且至少一个Worker心跳有效返回200，否则503。Worker心跳30秒失效。 |
| GET /api/v1/metrics | 登录后查看任务、推理和传输统计；`streamStates`给出各服务的状态数、容量与满载策略。 |

就绪检查反映API、数据库和Worker活性，不验证全部专项模型、摄像头、NVR或训练子进程，也不替代现场设备监控。模型推理仍要求CUDA，启动时检查GPU；GPU容量、推理错误仍需结合日志和metrics监控。

网络恢复时，任务和人工流程可按原请求编号重试。实时检测使用最新帧；429遵循Retry-After，409需要重新开始检测。不要用新的请求编号重复提交结果不确定的同一业务操作。

## 验证记录

单元和API回归覆盖清理回滚、文件占用后重试、长任务产物保护、媒体过期竞态、SQLite并发领取、租约耗尽指标、数据库故障、提交确认丢失、模型文件保护、流容量、流配置变化及采样与结束并发。

最终完整回归为358项通过、1项PostgreSQL专项测试跳过。真实螺丝视频上传浏览器验证也通过，覆盖历史记录后上传、连续再次上传、Worker执行和视频回放，产物位于`test-results/screw-upload-tests/run-7sbtoqle/`。

```powershell
npm test
npm run test:stability
```

`test:stability`创建独立临时数据库、随机端口API和Worker，结束时关闭自己创建的进程。参考图被编码为JPEG和短视频，使用真实CUDA模型，不改动本机业务数据。

2026年11月6日隔离验证结果（`test-results/backend-stability/run-gxp4456h/report.json`）：

- 同一会话6路HTTP采样流，各成功12帧，共72帧；6路状态全部保留。
- 20次繁忙响应为429，经测试脚本重试后完成。成功请求最长441.4ms，不含等待重试的时间，不等于相机采集到终端显示的端到端时延。
- 同时15个客户端执行300次健康探测，全部200。
- 推理中强制关闭Worker，30秒心跳过期后就绪返回503；重启Worker，租约恢复后第2次执行成功，产物可读取。
- 重启API后原会话、已发布产物和创建任务的幂等记录继续有效。

本机运行使用SQLite。本环境未配置PostgreSQL测试库，也未运行Docker镜像；相应并发测试明确跳过。部署前应使用独立PostgreSQL测试库运行专项测试，并在目标GPU服务器进行持续负载与故障演练。

## 协议中仍需完成的能力

| 范围 | 当前边界与后续验收 |
| --- | --- |
| 六工位自动流转 | 现有六工位是人工辅助记录；工位1孔→螺丝、工位5端子→螺丝有本工位约束。尚无同一工件跨工位1→6的统一自动放行状态机。 |
| 专项识别 | 孔位、黄色卡扣、接端子、两类吹净的现场模型与工艺标准需要数据和标定；人工记录不能当作自动识别通过。 |
| 相机与告警录像 | 浏览器上传JPEG采样已可运行；RTSP接入、自动告警视频片段、NVR联动、断网本地缓存补传仍需实施。 |
| 权限与报表 | 当前配置管理员账户；管理员/运维/操作工多角色、完整班次日报月报和Excel导出尚未齐备。 |
| 性能与可用率 | 6路HTTP参考图测试不能等同6台现场相机并发验收；15终端、≤500ms端到端、识别准确率、全年99%可用率和30天连续试运行需单独实测。 |

稳定性修复已经可用；以上缺口保持明确，避免把人工试跑、演示模型或短时测试标记为技术协议验收通过。
